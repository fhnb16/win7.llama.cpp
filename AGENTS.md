# Инструкции для AI-агентов

## Назначение репозитория

Репозиторий содержит GitHub Actions для сборки актуального релиза [llama.cpp](https://github.com/ggml-org/llama.cpp) под Windows 7 x64 и README. Workflow предпочитает новый стабильный релиз и использует более новый prerelease, когда стабильная версия уже собрана. Исходники llama.cpp клонируются workflow из upstream по тегу релиза; не добавляйте их копию в этот репозиторий.

Перед изменением поведения проверьте [.github/workflows/windows-7-release.yml](.github/workflows/windows-7-release.yml) и [README.md](README.md). README предназначен пользователям; этот файл — правила работы над репозиторием и обоснование архитектурных решений.

## Решения по сборке

- **Сборка CPU обязательна.** Она наиболее универсальна и должна быть успешной для публикации релиза.
- **Vulkan — дополнительная сборка.** Она использует отдельный build-каталог и отдельный архив `llama.cpp-<tag>-win7-x64-vulkan.zip`. Ошибка установки Vulkan SDK, конфигурации, компиляции, проверки или упаковки Vulkan не должна блокировать CPU-релиз. Vulkan-архив публикуется только после успешного прохождения соответствующих шагов.
- **Обе сборки используют w64devkit/MinGW-w64 и Win7 API-макросы** `_WIN32_WINNT=0x0601` и `WINVER=0x0601`. Не включайте CUDA или MSVC: эти сборочные пути не выбраны для цели Windows 7.
- **cpp-httplib патчится только на runner.** В upstream-релизе библиотека запрещает Windows ниже Windows 10 и использует Win8+ API для отображения файлов. Workflow снимает этот запрет и заменяет `CreateFile2`, `CreateFileMappingFromApp` и `MapViewOfFileFromApp` на Win7-совместимые `CreateFileW`, `CreateFileMappingW` и `MapViewOfFile`. Это сохраняет HTTP-сервер и не требует форка/копии библиотеки в репозитории. Патч должен проверять число совпадений и явно завершаться ошибкой при изменении upstream-кода; не ослабляйте проверку до молчаливой подмены или успешного пропуска.
- **Для Win7 при запуске требуется `--no-mmap`.** Отражайте это в инструкциях обоих архивов: иначе вызовы отображения файлов могут оказаться несовместимы с целевой ОС.
- **Проверка импортов WinAPI остаётся обязательной** отдельно для CPU и Vulkan: не публикуйте соответствующий архив, если исполняемый файл импортирует известные Win8/10-only API.

## Выпуск и триггеры

- Workflow запускается по расписанию, вручную и при push в `master`.
- На каждом запуске выбирается последний стабильный релиз upstream, если его тег ещё не опубликован здесь. Если последний стабильный тег уже собран, выбирается самый новый upstream prerelease, опубликованный позже стабильного, если этот prerelease ещё не собран. При отсутствии стабильных релизов используется самый новый prerelease.
- Тег локального релиза всегда совпадает с upstream-тегом; релизы, соответствующие upstream prerelease, публикуются с флагом GitHub prerelease.
- Уже опубликованный выбранный тег пропускается, чтобы расписание и push не пересобирали и не перезаписывали версию. Учитывайте это, когда меняете публикацию или добавляете поздние артефакты к существующему релизу.
- Для публикации нужно минимальное право `contents: write`. Не добавляйте права или секреты, не требуемые workflow.
- Пользователь сам управляет push/commit. Не отправляйте изменения и не создавайте коммиты без явной просьбы.

## Изменение и проверка workflow

- Сохраняйте PowerShell (`pwsh`) как shell скриптов Windows runner и существующий стиль явной проверки `$LASTEXITCODE`.
- Ошибки обязательных шагов должны останавливать публикацию. Для необязательной Vulkan-ветки используйте `continue-on-error` и условия по результату конкретного шага; не допускайте, чтобы неуспех Vulkan пометил весь job неуспешным или пропустил публикацию CPU.
- После изменений проверяйте синтаксис всех встроенных PowerShell-блоков. Для изменений патча применяйте его к чистым исходникам конкретного upstream-тега и проверяйте получившиеся файлы. Синтаксическая проверка не заменяет сборку.
- Если доступен GitHub Actions, проверьте фактический запуск: сначала обязательные CPU configure/build/package/API-check и публикацию, затем результат необязательных Vulkan-шагов. Не утверждайте, что сборка прошла, пока это не подтверждено runner-ом.
- При изменении имён архивов, триггеров, параметров сборки, патча или поведения fallback стабильного/prerelease обновляйте README.
